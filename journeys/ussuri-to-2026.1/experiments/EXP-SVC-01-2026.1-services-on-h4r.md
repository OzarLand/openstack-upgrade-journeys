## Pre-run declarations (written before the strict run)

**Expected attribute changes in the F2 read-back (dry runs `dry-f2-1`, `dry-f2-2`, `dry-all1`, `dry-d2`):**

1. `ports/aa5729b5-...` `binding:profile.trusted` is not returned by the 2026.1 API. Cause (verified in the database of the dry run): Neutron migration `5bcb7b31ec7d` (2024.2 expand) moves `binding:profile.trusted` into table `porttrusted` (row value 1) and empties `ml2_port_bindings.profile`; the key is shown as `port.trusted` only when ML2 extension driver `port_trusted` is enabled, which the Ussuri `ml2_conf.ini` does not do. Declared in `svc/expected-changes.json`.
2. Fields added by the 2026.1 APIs are listed, not compared (networks: qinq, vlan_transparent; security groups and rules: shared, belongs_to_default_sg, normalized_cidr, remote_address_group_id; subnets: router:external; servers: fault on ERROR servers). Not failures.
3. Differences in volatile fields follow `tools/inventory.py` (VOLATILE lists).
4. Compute services: the Ussuri rows are forced-down and the 2026.1 conductor/scheduler register as additional rows in the service list; counts are compared by object identity.

**Gate states built on disposable clones; deviations declared in advance:**

* The 2026.1 Nova API cannot modify an Ussuri `nova-compute` row: `PUT /os-services/<id>` returns HTTP 500 (`nova.exception.ServiceTooOld`) both for `--up` and `--down`, found in dry run `dry-abc2`. Therefore the rows are NOT changed through the API in states (a) and (b). The forced_down column of the Ussuri rows is set by one SQL `UPDATE` on the clone (`sqlforce` in the script, logged). The API attempt is recorded in the evidence. In the real procedure the Ussuri API is used before the bridge (DR-003 step 2); this only constrains how the lab builds states (a) and (b).
* The stock `nova.virt.fake.FakeDriver` cannot adopt an existing compute node (random per-process node uuid, "Duplicate compute node record"). The 2026.1 computes use `svc/ufj_fake2026.py`, a subclass whose node uuid comes from the compute_id file like a real single-node driver. The adoption path of the Nova manager, `_ensure_existing_node_identity` and the `compute_id` file, is real; the hypervisor is not.
* Configuration changes from the Ussuri-rendered files are listed in `lab/ussuri-db-lab/svc/config-changes.txt` (11 items: memcache backend, paste files, RabbitMQ quorum queues, removed scheduler filter, service_user, upgrade_levels=auto as Kolla templates it, debug).
* Lab wrapper change: `svc/wsgi/nt_app.py` imports all Neutron model modules and configures the SQLAlchemy mappers before the WSGI application (otherwise the first `GET /v2.0/ports` returns 500).

**Prediction under test:** (d) services start without the flag, `nova-status` "Older than N-1 computes" Success, no RPC cap cached until a 2026.1 compute is re-registered and forced-down cleared (then 6.x); (a) cap 5.11 and "Older than N-1 computes" Failure; (b) 6.x; (c) `nova-status` passes. Red Team claim to test in (a): an RPC-bearing operation fails under the 5.11 cap.

## Hypothesis

DR-003 (Agent 4 sharpening): with every Ussuri `nova-compute` row forced-down and the workaround flag unset, the 2026.1 control plane starts, `nova-status` "Older than N-1 computes" passes and no compute RPC cap is cached; after one host is re-registered and cleared, the cap is 6.x. Red Team RT-B-01: with unforced Ussuri rows and the flag set, the cap is 5.11 and an RPC-bearing operation fails.

## Findings beyond the stated hypotheses

1. **The 2026.1 Nova API cannot modify an Ussuri row.** `PUT /os-services/<id>` on a version-51 `nova-compute` row fails with HTTP 500 (`ServiceTooOld`), for both forced-down directions. DR-003 step 2 already requires the Ussuri API before the bridge; this confirms there is no repair path through the 2026.1 API for a row that was not forced-down in time. Clearing forced-down works only after the host re-registers (row version 72), which is the order DR-003 prescribes.
2. **The compute RPC cap exists only with `[upgrade_levels] compute = auto`.** The Ussuri-rendered `nova.conf` has no such line, and without it neither the cap nor the second gate exists. Kolla templates `auto`. The lab config was changed to match Kolla (`config-changes.txt`, item 11).
3. **The cap is computed lazily** at the first compute RPC of each process, so the log line appears after the first operation, not at start-up; state (d) shows the DEBUG line "Not caching ... min service_version is 0" only at DEBUG level.
4. **State (a) does not break operations in 2026.1**, because of the V5 proxy in the compute manager. The proxy is scheduled for removal; this property is release-dependent and must not be relied on for later releases. The control plane still correctly reports Failure in nova-status.
5. **Configuration needed to run 2026.1 on Ussuri-era files** (11 items, `svc/config-changes.txt`), notably RabbitMQ 4.4.0 refuses transient non-exclusive queues (`[oslo_messaging_rabbit] rabbit_quorum_queue`, `rabbit_transient_quorum_queue`, `use_queue_manager`, `amqp_durable_queues` required), `oslo_cache.memcache_pool` no longer exists (and `python-memcached` is still needed by the Keystone middleware), Nova's `AvailabilityZoneFilter` is gone, `[service_user]` is required by `nova-status`.
6. **Neutron: `binding:profile.trusted` is stored in `porttrusted` after the migration** and is not returned unless the ML2 extension driver `port_trusted` is enabled (F2 declared difference).
7. **Stock `nova.virt.fake.FakeDriver` cannot adopt an existing node** (random node uuid, "Duplicate compute node record"); the lab driver `svc/ufj_fake2026.py` reads the node identity from the compute_id file like the real drivers.
8. **Neutron under gunicorn**: without importing all model modules and `configure_mappers()` the first `GET /v2.0/ports` returns 500 (`Port.port_forwardings`, then `distributed_port_binding`) when the `port_forwarding` service plugin of the Ussuri config is enabled. Wrapper change in `svc/wsgi/nt_app.py`.

## Conclusion

The DR-003 preferred mechanism (state d) works on the real migrated database: with all Ussuri compute rows forced-down and no workaround flag, the 2026.1 control plane starts, `nova-status` passes the compute-age check, and the cap becomes 6.5 only after a 2026.1 compute re-registers and its forced-down flag is cleared. States (b) and (c) behave as designed. State (a) behaves as designed for the start-up gate (refusal without the flag, start with it) and for nova-status (Failure), and the cap is 5.11, but the predicted failure of an RPC operation did **not** occur (REFUTED for the operations tested). All pre-existing resources read back through the 2026.1 APIs with one explained difference (binding:profile.trusted). Deviations: states (a) and (b) were built with one SQL UPDATE of `forced_down` on the clone because the 2026.1 API refuses to touch Ussuri rows; the computes use a lab driver for node identity.

## Corrections (2026-10-31, after Red Team Stage 5c; the text above is kept as written)

* **RT-B-11, dataset tier.** The row "Dataset tier" above says "Tier-B lab dataset". That is wrong: the dataset is **Tier A** (synthetic, created through the Ussuri APIs, baseline v4). Tier B is reserved for sanitised production copies, so the production-copy prerequisite of architecture section 4 is **not** met by this record.
* **RT-B-12, title.** Read the title of this record as: **"2026.1 services start on the fast-forwarded databases and read back every pre-existing resource"**. What was shown is a list/show read-back of every pre-existing resource (F2), two-user authentication, credential decryption, image checksums, compute adoption, and lifecycle operations on **newly created** servers. Operations on **pre-existing** servers and volumes, and any Cinder data-path or Neutron binding call, belong to EXP-SVC-02 (record `EXP-SVC-02-*.md`).
* **RT-N-25, state (d) evidence.** The positive evidence that no compute RPC cap is cached in state (d) is `evidence/EXP-SVC-01/probe-d1-rpc/` (DEBUG line `Not caching compute RPC version_cap, because min service_version is 0 ... Defaulting to current version`), obtained in a supplementary run after the strict run with the same configuration (nova debug logging was on in the strict run, but the cap is only computed at the first compute RPC and the strict run issued none before the host was re-registered).
* **States (a) and (b) are lab-constructed.** In the status line and the conclusion, read "state (a)" and "state (b)" as **lab-constructed by one SQL UPDATE of `forced_down` on a disposable clone** (the 2026.1 API refuses to modify the Ussuri rows). They do not demonstrate that the Ussuri-API route produces the same rows, only that the 2026.1 services behave as described when the rows are in that state.
* **State (a) wording (Red Team 1.2 point 3).** The prediction is refuted for server create, stop, start, reboot --hard, pause and unpause on a **newly created** server under the 5.11 cap on a 2026.1 compute; cross-cell resize paths and the `compute-alt` fallback were not tested.
* **Driver change after this run.** `svc/ufj_fake2026.py` was extended afterwards for EXP-SVC-02 (it registers pre-existing guests on first use). SVC-01 ran with the version of commit `f1e64d3`; the change only affects instances that the fake driver does not know and none of the SVC-01 operations touched such an instance.

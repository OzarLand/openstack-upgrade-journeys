## 0. Verdict in one paragraph

**Experiments may start after corrective actions RT-B-01 … RT-B-05** (section 3). The database claims the architecture rests on are confirmed in source: Nova, Keystone and Cinder 2023.1 can take a Ussuri legacy database; the online data migrations that later code needs are either carried to 2026.1 (Nova, Placement) or correctly placed at the bridge (Cinder `use_quota`); Glance, Neutron and Placement chains are continuous; nothing that S2c skips exists only in 2023.2 / 2024.2 / 2025.2 code. Two things the architecture gets wrong or leaves unwritten are blocking: (1) the Nova service-version gate is **two gates, not one** — the FFU workaround flag only lets services *start*; the compute RPC version cap is derived from the same minimum-service-version query and is cached for the life of the process, so a 2026.1 control plane started while any non-forced-down Ussuri `nova-compute` row exists is pinned to RPC 5.11 and cannot drive 2026.1 computes (RPC target 6.5) until the rows are forced-down or re-registered **and** the services are restarted; (2) P2 must state that every Ussuri RPC/HTTP client on compute and network hosts is stopped before the 2026.1 control plane is reachable at the preserved endpoints and credentials. The experiment plan is well designed at the database layer but misses the rollback rehearsal and the idempotency re-run that my pre-registered criteria require, and it has no acceptance gate on baseline *content coverage*, without which the differential test is vacuous for the exact code paths that matter.

### 2.2 Is the differential comparison (01 vs 02 vs 03) a valid test of "skipping is equivalent"?

It is a **valid equivalence test and an invalid sufficiency test**. Two runs producing byte-identical normalised dumps prove that the *offline* S2c walk and the *offline* S2b walk do the same thing to this dataset. They do not prove that either produced a correct 2026.1 database, because both share every assumption below. Correctness comes only from the invariants against T0 (C5–C7) and from the API read-back (F2), never from 01 = 02.

Blind spots, in order of consequence:

1. **Neither run executes a service.** The staircase that upstream actually tests (S1) has V, W, X, Y, Z, 2023.1, 2024.1, 2025.1 *services* running between syncs. Those services upgrade objects on load/save (`request_specs.spec`, `instance_extra.*` — V20 is the proof of class), run periodic tasks (`_sync_power_states`, `update_available_resource`, Neutron agent resync, Placement inventory/allocation reconciliation), and emit the data the *next* release's ODM expects. S2b at DB level is **not** S1; calling 02 "the reference" overstates it. The architecture must say "DB-level staircase", and treat 01 = 02 as a necessary condition only.
2. **Lazy object conversion is invisible to dumps.** A Ussuri-era blob that 2026.1 can load (because conversion code survived) and one it cannot look identical in 01 and 02. Only F2 with *every* instance/port/volume loaded, plus log scanning for `IncompatibleObjectVersion` / `ObjectActionError` / `KeyError`, tests this — and only for blobs the baseline contains.
3. **Start-up reconciliation happens once, at 2026.1.** `nova-compute` adopting a node (V16), machine-type recording (libvirt only — never exercised by the fake driver), Neutron agent re-registration, Placement provider re-creation if UUIDs drift: none of this is in 01/02/03. The fake driver cannot show `hw_machine_type` recording, CPU-model or disk-bus regeneration; those stay `Not validated` whatever the lab shows.
4. **Migration-time randomness and timestamps make 01 ≠ 02 by construction.** Neutron `c33da356b165` generates row UUIDs at migration time (V10); ODMs touch `updated_at`; Cinder `9c74c1c6971f` stamps `created_at = now()`. The normalisation must exclude these columns explicitly, and every excluded column is a column where a real difference would also be hidden. Write the exclusion list *before* R1 and keep it minimal.
5. **Data the baseline lacks is untested, silently.** Code paths with zero matching rows pass trivially: `use_quota` on temporary/migration-target volumes, `populate_instance_compute_id` on instances whose node is gone, `b4f8b3f584e0` on duplicate trusts, `b1bca967e19d` on duplicate segment ranges, `054e34dbe6b4` on non-empty plugin tables, PCI `populate_dev_uuids`, shadow tables, soft-deleted instances. → section 2.3.
6. **Ordering effects between hops are compressed.** In S1 every release's ODM ran against rows written by that release's services; in 01 all ODMs of a hop run against Ussuri-shaped rows only. Nova's "ODM complete before next upgrade" rule is honoured syntactically, not semantically.
7. **03 (S2a) adds little.** Since 2026.1 carries every ODM and chain (V5–V8), 03 ≠ 01 would be a finding about 2024.1/2025.1 code side effects (`9c74c1c6971f`, `b7b88f50aab5` run with 2024.1 code in 01 and with 2026.1 code in 03 — same files). Keep it, lowest priority, as a cheap consistency check.

## 5. Rulings on the open decisions (architecture §5)

1. **Nova service-version gate — mechanism.** Neither option alone. Ruling: **fence → forced-down all Ussuri compute rows → start control plane (flag set, time-boxed) → re-register hosts one by one and clear forced-down each → remove flag and restart control services.** Grounds: the flag addresses only start-up (V13); the RPC cap is a second gate on the same query (V15); forced-down is the only state that excludes rows from both queries without deleting them (V14), and deleting rows breaks node adoption (V16). Agent 4's "do not change real state" is honoured in substance: forced-down asserts a state that fencing has already made true, which is also the `openstack-incident-analysis` rule (fence before anything that looks like evacuation). Agent 6's evacuation flow is accepted **only** for the shared-storage class and only after the fencing proof. The two-state test in RT-B-01 is the experiment that settles it.
2. **Bridge release.** **2023.1**, as proposed; Zed stays the documented fallback if 2023.1 packages do not co-install under its upper-constraints. Grounds: identical bridge code (V1–V3); 2023.1 is the SLURP start, carries the last and most-patched copies of the legacy repos, Python 3.8–3.10 classifiers, and the NUMA object fix (V20). No evidence favours Zed.
3. **Engine path.** **Not decidable before the experiments; run both E1 and E2 lines, and E3 only as a negative/informational run.** For production, my pre-registered criterion B.4 stands: in-place stepwise is acceptable only with vendor documentation (unreachable here) plus a 3-node Galera rehearsal; otherwise **dump/restore into a fresh 11.4 cluster (E2), declared as a rebuild**, is the default. The Galera cluster is rebuilt by SST in P2 anyway, so E2 costs no extra outage class; its specific risks (charset/collation drift for tables without explicit charset, definers, `--hex-blob`, restore time) must be covered by the schema diff (C4) and by timing on Tier B. The "bridge code on 10.6 vs everything on 11.4" second line of 04 §2 is required, not optional, because the production E2 variant would run 2023.1 code against 11.4.
4. **Can a PyPI/fake-driver container lab support `LAB-VALIDATED` for the database claim?** **Yes, for one narrowly worded claim, and the wording is mandatory on every record:** "`LAB-VALIDATED` — scope: database schema and data migration Ussuri → 2026.1 by the S2c code sequence, using upstream service code installed from PyPI under each release's `upper-constraints`, standalone MariaDB library images (no Galera), synthetic Tier A dataset generated through Ussuri APIs with the fake virt driver, no Kolla images, no Kolla-Ansible, no data plane. Not shown: Kolla image behaviour, Galera, production data, durations at production scale, live instances, libvirt-specific reconciliation (machine type, CPU model), RabbitMQ, host OS." Anything beyond that (Tier B, Kolla images by digest, Galera) moves the record to `NEEDS-REVALIDATION` until re-run. The brief's rule "never present an unsupported procedure as supported" is not satisfied by the label alone; the record must also carry the classification **Technically possible but unsupported** of the procedure itself.
5. **P4 as fallback.** **Keep, but rename its promise.** P4 does not "isolate P2's biggest unknown"; it relocates it: it avoids the Nova object-blob question by accepting every Strategy C cost (new instance/volume/port UUIDs, per-instance copy, split-brain hazard) while still running the unsupported Keystone bridge. Its split line is nevertheless the right one if a hybrid is ever needed (Keystone IDs are the root of every cross-service reference; Glance image IDs are referenced by instances and volumes and are the only API-settable IDs). Conditions to keep it: the dependency table my D-criterion requires (which IDs cross the line and how each is preserved), and no experiment budget beyond what EXP-DB-01 already yields for Keystone and Glance.

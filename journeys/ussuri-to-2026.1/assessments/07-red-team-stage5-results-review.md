## 0. Verdict in one paragraph

The lab engineer's four records are, in their headline statuses, honest: EXP-DB-00 is `LAB-VALIDATED` for restorability only, N1 is a confirmed negative, R0 is a calibration with amendments left for me, and EXP-DB-01 is `FAILED` under the frozen rules with an informational completed run clearly marked as not a pass. Underneath the headlines the evidence shows four things the records do not say or say wrongly, and two of them block the strict re-run: **(1)** the live R1c run reported `undeclared=5` for H4 and H4r, the comparator was edited 40 seconds after the run ended, and every `data-diff.txt` of R1c was regenerated with it; the five items and the comparator change are nowhere recorded (RT-B-06). **(2)** The frozen pre-check **PC-C1** ("`use_quota` NULL = 0 after the 2023.1 ODM, STOP before H2") is not implemented in any script, so the Cinder failure at H2 was reached through a missing safeguard, not only through a code gap (RT-B-07). **(3)** The R0 and EXP-DB-01 records both claim that after the six amendments nothing else differs; the evidence shows a seventh, real, transient schema difference at H2 (`neutron.portnumaaffinitypolicies.numa_affinity_policy` enum lacks `'socket'`), explained by source but undeclared (A7). **(4)** The "cause" written for the Cinder failure ("the code says it covers deleted rows") is refuted by the 2023.1 source: the ODM runs under an admin context whose `read_deleted` defaults to `'no'`, and the frozen V-C1 text that cites `read_deleted='yes'` is wrong. Baseline v2 was a legitimate correction of a lab-made defect but it also removed a legitimate production pattern from the dataset; baseline v3 (`cinder-manage db purge 0`) moved the goalposts: it deleted the only rows that exercise the defect, removed a checklist item, and is not an acceptable production step without a separate operational decision. I **accept A1, A2 and A5, accept A3, A4 and A6 with conditions, add A7, and reject nothing**, with the conditions in §2. N1 does confirm that 2026.1 code cannot take a Ussuri database, but not by "refusing": it tries to create the schema blindly, and the empty `alembic_version` it leaves is a pre-check item for production, not a danger to the 2023.1 bridge (§3). The v3 run establishes that the S2c *code sequence* executes end to end with no hand edit on a dataset without soft-deleted Cinder rows and that a second 2026.1 pass changes nothing; it does not establish anything about Cinder on a real dataset, and until RT-B-06…RT-B-10 are closed EXP-DB-01 stays `FAILED` and Cinder's part of S2c is `Not validated` for every dataset that has ever deleted a volume or snapshot (§4).

## 3. EXP-DB-N1: what "Table already exists" proves, and the empty `alembic_version`

**What it proves.** The pre-registered negative (architecture §4: "2026.1 code refuses a Ussuri database") is confirmed in substance and wrong in its verb. 2026.1 `db_sync` for Nova, Keystone and Cinder contains no legacy-detection branch (`nova@origin/stable/2026.1:nova/db/migration.py:61-91`; `keystone@origin/stable/2026.1:keystone/common/sql/upgrades.py:_db_sync`; `cinder@origin/stable/2026.1:cinder/db/migration.py:db_sync`). It reads `alembic_version` (absent), concludes "fresh database", and runs the squashed initial revision, which collides with the first table it tries to create. The result is therefore stronger than a refusal: **there is no code path at all**, and the failure mode is an accident of table order, not a guard. The classification **Incompatible** for the direct jump stands, on the evidence of the lab plus the source. The record's conclusion "an operator who ran it against a production database would see the same" is correct and should add: *and would see it only because `cell_mappings`, `instances`, `application_credential` and `services` happen to be the first `CREATE TABLE` of each revision*.

**The operational danger of the empty `alembic_version`.** I checked the three bridges against it:

- Nova 2023.1: `_is_database_under_alembic_control` = `bool(MigrationContext.get_current_revision())` (`nova@2023.1-eom:nova/db/migration.py:84-87`); an empty table yields `None` → `False`; the legacy branch then runs and `alembic stamp` inserts the row. **The bridge still works.**
- Keystone 2023.1: `bool(context.get_current_heads())` (`keystone@2023.1-eom:keystone/common/sql/upgrades.py:153-156`) → empty tuple → `False`. **Works.**
- Cinder 2023.1: same pattern (`cinder@2023.1-eom:cinder/db/migration.py:77-80`). **Works.**

So the danger is not to the bridge code; it is to **people and tooling**: (a) any check of the form "does `alembic_version` exist?" (a runbook step, a Kolla task, a human) now answers yes for a database that is still legacy, and `nova-manage db version` / `keystone-manage db_version` print nothing useful; (b) the DDL is non-transactional: the clean outcome depended on the *first* statement failing — a future initial revision that begins with a table absent at Ussuri would leave partially created tables, and the later bridge's `migrate_api.upgrade()` or `alembic upgrade` would fail on "already exists" with no clean way back except restore; (c) a second wrong attempt, or a `kolla-ansible deploy` of 2026.1 against the untouched database, repeats the attempt every time and leaves the same state. **Ruling:** the production pre-check list gains **PC-V3**: "no `alembic_version` table exists in `nova`, `nova_cell0`, `nova_api`, `keystone`, `cinder` before the bridge; if one exists, STOP — newer code has touched this database; establish what ran and restore from the pre-touch backup". Dropping the empty table by hand is a bookkeeping edit (SC-HAND) and is not the answer; restoring is. The record's suggestion "a later bridge run must expect it" is true but invites tolerance of a state that should never be reached.
